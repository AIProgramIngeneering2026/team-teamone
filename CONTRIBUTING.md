# Правила совместной разработки

Документ описывает, как команда TeamOne работает над CampusSpot, сервисом
бронирования коворкингов и свободных аудиторий кампуса. Задачи, код и ревью
ведём в репозитории `team-teamone`. Отчёты по практикам сдаём в `Zadania`.

## 1. Задачи (GitHub Issues)

- Перед началом работы создаём или берём существующую задачу (Issue).
  Указываем исполнителя, ожидаемый результат и критерии приёмки.
- Если задача связана с бронированием, указываем сценарий из
  `docs/requirements.md`. Например, заявка на аудиторию отклоняется,
  если на выбранное время запланирована пара.
- Изменения API, формата данных и переходов между состояниями заявки
  (`Job`) заранее согласуем с участниками, чей код они затронут.
- Если за 48 часов до срока сдачи практики у задачи ещё нет PR, другой
  участник может взять её, указав это в Issue и сменив исполнителя.

## 2. Ветки

- Создаём отдельную ветку для каждой задачи от актуальной `main`.
  Изменения в `main` попадают через Pull Request. Прямой push и force push
  в `main` запрещены.
- Используем формат `<тип>/<номер-issue>-<краткое-описание>`.

  - `docs/12-classroom-conflict` — описать пересечение брони с учебной парой.
  - `feat/14-booking-limits` — добавить проверку лимитов бронирования.
  - `fix/15-release-cancelled-slot` — освободить интервал после отмены брони.
  - `test/16-job-states` — проверить переходы между состояниями заявки.

- Несвязанные правки делаем в отдельных ветках и PR. Если несколько
  участников редактируют `docs/requirements.md`, заранее делим разделы,
  вливаем PR по очереди и перед слиянием сверяем изменения с актуальной `main`.

## 3. Коммиты

- В одном коммите сохраняем одно законченное изменение. Например, исправление
  ошибки и тест, который её воспроизводит, можно включить в один коммит.
- Сообщение пишем в формате `<тип>: <краткое действие>`. По нему должно быть
  понятно, что изменилось.

  - `docs: описать пересечение брони с учебной парой`
  - `fix: освободить интервал после отмены брони`
  - `test: проверить переход заявки в EXPIRED`

## 4. Pull Request

1. Открываем PR из своей ветки в `main` репозитория `team-teamone`.
2. Добавляем ссылку на Issue. Если PR завершает задачу, пишем `Closes #12`
   с её номером. Если закрывает только часть задачи, пишем `Refs #12`.
3. Описываем, что изменилось, зачем и как проверить результат. Если есть
   ограничения, указываем их в описании PR.
4. Назначаем другого участника на ревью. После существенных правок
   повторно запрашиваем проверку.
5. Вливаем PR после одобрения другого участника, устранения существенных
   замечаний и прохождения обязательных автоматических проверок, если они
   настроены. Одобрение и проверки должны относиться к итоговой версии PR.

## 5. Code Review

- Распределяем ревью по кругу. Каждый участник проверяет PR следующего
  участника по согласованному списку. Если проверяющий недоступен, команда
  назначает замену.
- Сначала читаем Issue и описание PR, затем смотрим вкладку **Files changed**.
  Сверяем изменения с критериями приёмки и проверяем обработку ошибок.
- Для кода проверяем затронутые сценарии. Например, при изменении проверки
  конфликтов смотрим, отклоняется ли бронь, которая пересекается с парой
  или уже подтверждённой бронью.
- Для документации проверяем структуру, ссылки и формулировки. Сверяем
  сценарии и состояния `Job` с `README.md` и `docs/requirements.md`.
- Оставляем хотя бы одно замечание, предложение или вопрос по существу.
  Для практики одного `LGTM` недостаточно. Автор отвечает на замечания
  и вносит согласованные исправления.

## 6. Definition of Done (критерии готовности)

Задача готова, когда выполнены все применимые пункты.

- Критерии приёмки выполнены. В PR указано, как проверили результат.
- Для изменений в коде добавлены или обновлены нужные тесты. Проверены
  затронутые сценарии, например повтор заявки с тем же ключом
  идемпотентности, превышение лимита или попытка брони без нужных прав.
- Документация соответствует поведению API и разрешённым переходам
  `Job`. При изменении схемы базы данных добавлена миграция.
- Обязательные автоматические проверки прошли, если они настроены.
- Другой участник одобрил итоговую версию PR, существенные замечания
  устранены, PR влит в `main`, а задача закрыта или отмечена выполненной.

## 7. Учёт личного вклада

- Сохраняем полные ссылки на свои влитые PR и на содержательные ревью
  чужих PR за каждую практику. По общим правилам курса личное участие
  подтверждается любым из этих двух видов работы.
- По заданию первой практики каждый участник делает оба вида работы.
  У него должны быть свой влитый PR и содержательное ревью чужого PR.
- Команда сдаёт один PR с отчётом `teams/teamone/pN.md` в `Zadania`.
  В разделе «Вклад участников» приводим ссылки по каждому участнику.

## 8. Использование ИИ

ИИ можно использовать для работы с кодом и документацией. Автор проверяет
предложенные изменения, исправляет ошибки и может объяснить результат.
Пароли, токены доступа и другие секреты не добавляем в репозиторий и промпты.
